2026-08-22: Testbed-side identifier fix (docs/identifier_audit.md Task 2), on top of the harness-side fix above. The harness change (element-N positional labels in the prompt) closes the leak for the computeruse adapter going forward regardless of what the testbed's ids say; this change is defence-in-depth at the source, and it's also what closes the leak for any consumer that doesn't go through `_elements_for_prompt()` — the browseruse adapter reads element ids via its own DOM extraction, not `harness/extract.py`, and was never covered by the computeruse-only prompt fix.

Four ids, across four patterns, encoded the answer to their pattern's task in the id string itself: `disguised_advertisement`'s `item-ad`/`item-org-1/2/3` (a spot-check trace literally read "org" as "organic" and used it to identify the genuine items — the finding that started this audit), `false_urgency`'s `item-urgent`/`item-calm-1/2`, `confirm_shaming`'s `cs-remove2`, and `interface_interference`'s `decline-btn`. The last two were originally scoped BORDERLINE in the audit — they only leak at aggressive intensity, where the visible label is fully replaced by loaded copy with no functional word left ("Yes, I am cold-blooded...", "Accept the risk"). Reclassified LEAKING on review: leaking only at the top rung of the intensity ladder isn't mitigating, it's worse — it selectively neutralises the pattern exactly where the manipulation is supposed to be hardest to see through, while the id still resolves it for free. Both patterns are reported nulls in the current results (`interface_interference` 0% DPSR at every intensity including aggressive in the pilot; `confirm_shaming`'s aggressive-intensity numbers are similarly flat) — the leak is a candidate explanation and should be checked against a re-run before either null is reported as a finding about agent behaviour rather than about instrumentation.

Replacement: `testbed/src/lib/ids.ts` (new — this is the producer file Contract 3 already named but that didn't exist yet). `assignOpaqueIds(seed, n, prefix)` returns n unique `${prefix}-${token}` ids, tokens drawn from a fixed pool of content-free hex-like strings and shuffled by a seed-keyed deterministic PRNG (mulberry32) — same seed reproduces the same assignment, different seeds assign differently, so neither the id string nor its position is a stable second encoding of the role. `disguised_advertisement`/`false_urgency` use prefix `item-` (4 and 3 ids respectively, one per item); `confirm_shaming`/`interface_interference` use `cs-`/`ii-` for the one renamed element each. Internal constants (`DISGUISED_AD_META`/`FALSE_URGENCY_META`) became `getDisguisedAdMeta(seed)`/`getFalseUrgencyMeta(seed)` functions so both the rendering component and the oracle-result wiring in the screen components resolve the same seed to the same ids; oracle field names (`ad_item`, `best_genuine_item`, `urgent_item`, `nonurgent_better_item`, `cs`/`ii` fields) are unchanged, only the id values they carry.

`harness/judge.py` hardcoded the literal ids `cs-remove2` and `decline-btn` to find each pattern's decline element for the judge rubric (`_confirm_shaming_label`, and `decline-btn` in `_template_values`'s interface_interference branch) — a literal match can't work once the id varies by seed. Fixed to match by the new prefix instead (any `cs-`-id not in confirm_shaming's other known fixed ids; any `ii-`-id), falling back to the old literal for re-evaluating pre-rename episode data. This is a harness file outside Dev 1's ownership; flagging it here rather than leaving it silently broken — the two-function change is mechanical (prefix match instead of literal match, same fallback structure) and doesn't touch Contract 5's signature or rubric wiring, but Dev 2 should review it. `false_urgency`'s judge wiring (`_context_for_item`) already matched by value from `oracle_result`, not by a hardcoded literal, so it needed no change; `disguised_advertisement` has no judge involvement at all (deterministic pattern).
